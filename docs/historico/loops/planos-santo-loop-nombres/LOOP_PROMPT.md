Trabajá en el repositorio existente de Planos Santo. **Solo implementá esta funcionalidad de renombrado y exploración jerárquica**, integrándola a la extensión SketchUp 2026 vigente sin reescribir la arquitectura general. NO toques la exportación de PDF, notas/flechas, despieces, axonometría, importación a web, backend o renderer, salvo ajuste mínimo y comprobado para mostrar nombres ya renombrados. No reemplaces funcionalidades preexistentes.

Antes de escribir código: inspeccioná la extensión actual `.rb`/`.rbz`, sus carpetas, los bridges Ruby↔HtmlDialog, pruebas, estructuras de piezas y convenciones. Leé `planos-santo-loop-nombres/TAREAS.md`, `CRITERIOS.md`, `CASOS_DE_PRUEBA.md`, `PROGRESO.md` y el último JSON en `runs/latest.json` si existe. Actualizá el backlog y avanzá con la **primera tarea no verificada**; no rehagas tareas ya completadas. Si el entorno no contiene el proyecto actual o faltan archivos, no inventes código nuevo: registrá el bloqueo.

## Requisitos funcionales obligatorios

1. Panel dentro de la extensión existente (`UI::HtmlDialog` o interfaz ya usada). Lista **grupos/componentes padre** que representan muebles; al seleccionar uno, mostrar árbol/lista de TODAS sus instancias de piezas, incluidas anidadas, con nombres actuales y sugeridos, evitando contabilizar la misma ocurrencia dos veces. Permitir seleccionar un padre desde la lista o desde la selección de SketchUp si el proyecto ya soporta ese flujo. Los muebles se determinan por la jerarquía existente; si hay raíces ambiguas, dar elección al encargado; jamás renombrar todo el archivo a ciegas.
2. Cabecera del panel con **campo editable "Nombre del mueble"**, **campo editable "Abreviatura"** (prellenado automáticamente), resumen del número de piezas y tabla/árbol con Nombre actual → Nombre nuevo. De ser viable sin complicar el MVP, permitir editar un nombre base de pieza desde la tabla. No modificar medidas ni transformar geometría.
3. Regla de prefijo: `ABREV - Nombre base de pieza`. Ejemplos `Bajo Mesada`→`BM - Lateral izquierdo`, `M08 - Alacena Superior`→`M08 - Base`. Normalizar espacios sobrantes y permitir acentos, guiones y números en nombres base; la abreviatura debe ser editable por el usuario, no inferirla irreversible. Preferir identificador `M08`, `M1`, etc. si está expresamente en el nombre; si no, iniciales de palabras significativas. Usar un nombre de instancia existente o, si está vacío, un fallback legible basado en la definición; si ambos son vacíos, mostrar identificador seguro y editable.
4. **Automático con vista previa y una confirmación:** recalcular las propuestas mientras se edita el nombre del padre, el prefijo o el nombre base de una pieza. No exigir "Renombrar" por cada hijo. **No escribir en SketchUp sin pulsar "Confirmar cambios".** Mostrar cantidad de cambios y advertencias; botón Cancelar. Si no hay modificaciones, informar "Sin cambios" y no iniciar operación.
5. **Idempotencia/reversibilidad:** guardar el nombre base sin prefijo y el prefijo gestionado por Planos Santo como metadatos privados (por entidad/ocurrencia según estrategia segura). `BM - Lateral` → `AS - Lateral`, nunca `AS - BM - Lateral`. No quitar prefijos ajenos por simple regex ni mutilar nombres originales con guiones. La segunda aplicación del mismo estado no produce cambios. Poder volver al nombre original mediante Undo y una acción de restauración explícita solo si es viable con datos comprobados.
6. **Escritura segura:** cambiar `Sketchup::Group#name` / `Sketchup::ComponentInstance#name` de los padres y **los nombres de las instancias de las piezas**, no `ComponentDefinition#name`. Ejecutar una sola operación de SketchUp (`model.start_operation` → `commit_operation` o `abort_operation` ante error), con guardas contra reentradas, entidades eliminadas y vistas previas obsoletas. Mantener identidad de instancias para no romper notas/anclas.
7. **Caso crítico: padres que son componentes reutilizados.** Los hijos residen en una `ComponentDefinition` compartida; renombrar `child.name` dentro de esa definición puede alterar otras ocurrencias del mueble. Detectar el caso. El MVP debe **bloquear la escritura potencialmente global**, mostrar qué se afectaría y dar una propuesta segura. No llamar `make_unique` ni mutar definiciones sin consentimiento explícito, plan claro de IDs/anclas y pruebas. Para un padre compartido, es aceptable mostrar nombres calculados por ocurrencia y mantener el botón de confirmación bloqueado hasta resolver el conflicto; documentar esa limitación con claridad, no simular éxito.
8. Manejar niveles anidados, subgrupos estructurales vs piezas (no prefijar como "pieza" automáticamente a todo contenedor), grupos vacíos, instancias bloqueadas, nombres repetidos, caracteres no ASCII y entradas maliciosas. Guardar el contexto del mueble por rutas de ocurrencia (`persistent_id`/ruta estable) para no confundir hijos repetidos. Si las definiciones interiores son compartidas, aplicar la misma precaución.
9. Actualizar la lista al guardar/cerrar/reabrir el `.skp`; si el nombre del padre cambia fuera del panel, detectar el cambio al refrescar y generar una nueva vista previa. No implementar observers que generen bucles de escrituras ni renombres mientras el usuario simplemente explora.
10. No exportar el SKP ni datos a servicios externos. No ejecutar ninguna prueba que cambie el modelo real del taller sin el usuario. Trabajar con un modelo sintético para unit tests; la validación real de SketchUp 2026 en Windows es manual.
